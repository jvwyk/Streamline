# ONBOARDING.md — your first session

> If you're a new agent landing on this repository, this is the doc that
> gets you productive in 15 minutes. Read it first.

## Reading order, with stop conditions

> AGENTS.md (operating principles) → HANDOVER.md (working knowledge) →
> PHASE-1-CLOSEOUT.md (what's built) → skim streamline-plan.md → skim
> PARKED.md. Don't read OBSERVATIONS.md, TESTING.md, WORKFLOW.md cover-to-
> cover; consult them when working in their domains.

## What your first session looks like

> User sends a sub-phase prompt → you plan → surface design questions →
> wait for confirmation → implement per the rhythm → stop at sub-phase
> boundary → report using standing format. The first prompt you receive
> after Phase 1's close opens Phase 2 with P-5 (TimeProvider) and P-11
> (handler ↔ persisted batch status) as first-tier design questions;
> HANDOVER.md §3 explains why.

## Quick-reference tables

> When to "stop and ask" vs. proceed. When to "stop and report" vs.
> continue into the next sub-phase (never — but the distinction matters).
> When to surface a parked decision vs. resolve in-place vs. defer to a
> phase. What "stop and report" looks like vs. "stop and ask."

## Where to find what

> PARKED.md for deferrals; PHASE-N-CLOSEOUT.md for prior phase summaries;
> src/ for code patterns; TESTING.md for test discipline; WORKFLOW.md for
> commit format; OBSERVATIONS.md for the observation catalog and emission
> rules; STANDARDS.md for the rules indexed.

## The standards bar

> Tests required for every production change. Commits individually
> revertable. Plans written and confirmed before code. Design questions
> surfaced explicitly. Parked decisions get phase ownership. Concrete
> examples of "meeting the bar" vs. "below the bar" from Phase 1.

## The first thing to do on landing

> Read the docs in the order above. Confirm to the user that you've loaded
> the context. Wait for the next prompt. Don't speculate about Phase 2
> design before reading PARKED.md and HANDOVER.md §3.
